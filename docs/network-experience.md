# 现在这套方案，怎么用得更舒服

这台 RD03v2 现在运行小米原厂 **2.0.28**，由路由器上的标准 MiniEAP 完成校园网认证，再通过私人 Wi-Fi 分给电脑和手机。日常使用已经走通，接下来最值得花时间的是无线覆盖、多人使用时的延迟，以及找出外网速度的瓶颈。

## 保留原厂，还是换 OpenWrt

本次选择保留原厂，是因为已经在这台机器、这个宿舍墙口上完成了认证、获取地址和联网，也保住了现有无线环境。它解决的是「让路由器接替电脑认证，给自己的设备共享上网」这个需求。

OpenWrt 更适合另一类需求：希望使用它的软件包、管理方式和网络功能，并愿意围绕这些功能维护一套系统。对本机来说，这是一项后续改造，而不是当前方案已经完成的步骤。

| 你关心什么 | 当前原厂方案 | 如果改用 OpenWrt |
| --- | --- | --- |
| 日常联网 | 认证、DHCP 和多台设备分别上网已有实测 | 需要在目标系统上重新完成这些验证 |
| 调整与扩展 | 围绕这台原厂系统配置，部分管理依赖脚本 | 可以围绕对应构建的软件包和服务机制组织配置 |
| 无线与速度 | 有当前机器的实测基线 | 要比较目标构建的无线、转发和负载表现 |
| 维护成本 | 继续维护已有配置与恢复逻辑 | 多一项固件支持、安装和故障恢复的维护工作 |

目前有的是原厂 2.0.28 的实测记录；OpenWrt 还没安装，也没有同机 A/B 对照。如果准备换系统，可以先列出想增加的功能，再比较它的实际收益和维护成本。[OpenWrt 设备页](https://openwrt.org/toh/xiaomi/ax3000t)可作为查找入口；选镜像时要核对 **RD03v2**，不能只看「AX3000T」这个商品名。

## 1. 先改善设备到路由器这一段

同一条校园出口，手机放在不同房间、连接不同频段，体验也可能差很多。先用一台常用设备，在实际使用位置比较私人 5GHz 和 2.4GHz：除了下载速度，也看网页是否卡顿、延迟是否跳动。大流量设备可以先试 5GHz，距离远、隔墙多的位置再比较 2.4GHz。信道和带宽也按这个办法选，每次只改一项，留下改前、改后的结果。

投屏、打印和设备发现则是另一件事：它们需要下游设备之间能够互通。本次已查看主 AP 的桥接与隔离配置，下一步是拿两台私人 Wi-Fi 下的设备实际测试发现和传输，保持校园 WAN 与私人 LAN 分开。

目前已有四台设备各自上网成功的反馈；四台同时持续使用、广播和组播发现还没有验收。设备能连上多少，与同时用起来是否流畅，也应分别记录。

## 2. 让下载、上传和日常操作少互相拖累

如果一台设备开始上传，其他设备的视频会议、游戏或网页就明显卡顿，先测「忙的时候延迟增加了多少」。把空闲、适度下载、适度上传三种状态放在相近时间比较，同时记录吞吐、延迟、丢包和路由器 CPU，能更快判断是否存在排队问题。

本次原厂配置中，QoS 关闭，也没有配置上下行限速；NSS/ECM 组件已加载。这些读数可以作为后续调整的起点，实际效果仍要在负载下比较。

若确实测到明显的排队延迟，再考虑队列管理。它的取舍很具体：可能让多人使用更顺畅，也可能牺牲部分峰值吞吐并增加 CPU 负担。[OpenWrt 的 SQM 文档](https://openwrt.org/docs/guide-user/network/traffic-shaping/sqm)介绍了这条思路及其与流卸载的关系。它适合作为功能选择的依据，具体到 RD03v2 的构建和原厂系统，要分别评估实现方式。

这一步追求的是「有人下载时，其他人还能舒服地用」，不只是测速数字更大。

## 3. 找出外网速度真正卡在哪一段

千兆 WAN 表示墙口到路由器的链路协商速率。外网下载还要经过校园出口、测试服务器，以及设备到路由器的连接，不能把这几个速度画等号。

本次凌晨和上午的下载、上传结果波动较大，具体数字见[现场结果](field-results.md)。现有样本还分不出账号策略、校园忙闲、测试服务器和本地链路各占多少影响，也就没有证据把波动直接归为账号限速。

下一轮可以这样缩小范围：

1. 选同一测试目标、相同数据量，在相近时段重复取样，确认每次传输收齐数据。
2. 条件允许时比较电脑直连校园网、路由器有线下游、私人 Wi-Fi，逐段看速度和延迟在哪里变化。只有一根网线时分时完成，并把测试时间一起记下。
3. 同时保留认证、DHCP 和 DNS 状态。这样再遇到「有时上不了」，能区分出口掉线、解析失败和单个网站变慢。

这轮检查先沿用正在工作的认证会话。反复重启认证客户端会改变测试条件，也容易把原来的速度问题混进新的会话故障。

## 接下来还要补哪些实测
