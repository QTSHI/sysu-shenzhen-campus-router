# 原厂与 OpenWrt：网络体验应怎样比较

本项目实际运行的是 **RD03v2 原厂 2.0.28 + 标准 MiniEAP**，没有刷 OpenWrt，也没有在同一台机器上完成原厂与 OpenWrt 的 A/B 测试。当前能讨论的是已测结果、两条路线的条件，以及下一步怎样改善，不能给出“刷后一定更快”的结论。

## 两条路线的现实差别

| 项目 | 本次原厂路线 | OpenWrt 路线需要重新证明 |
| --- | --- | --- |
| 校园认证 | 当前墙口 MD5、Success、DHCP 和来源绑定访问已通过 | 对应构建的接口、认证客户端、依赖和生命周期 |
| 无线与加速 | 主 AP、桥和现有加速组件已有现场读数 | 对应硬件的无线驱动、加速能力及实际性能 |
| 配置与服务 | 固定原厂环境下的受控管理、单客户端与失败锁存 | 软件包和服务机制不同，原厂脚本不能原样套用 |
| 更换系统的代价 | 保留原固件；没有刷写固件或原始分区、修改启动环境，程序配置存数据目录 | 精确硬件支持、镜像来源、备份与可验证恢复条件 |
| 性能证据 | 两个时段的小样本，详见[现场结果](field-results.md) | 同时段、同目标、同传输方式的对照结果 |

AX3000T 的名称不足以判断兼容。[OpenWrt 设备页](https://openwrt.org/toh/xiaomi/ax3000t)专门区分 RD03/RD23 与架构不同的 RD03v2；具体支持和社区构建状态还需按准备变更时重新核验。不能把其他版本的安装文件或经验直接套给本机。本仓库不提供这条路线的刷写步骤。

本次原厂诊断看到 QoS 关闭、没有配置上下行限速，NSS/ECM 组件已加载；这不证明每条流都在硬件卸载，也不证明原厂已经没有性能瓶颈。凌晨短测的重叠 CPU 样本不高，只说明那一次小负载窗口，没有覆盖持续满载、无线竞争或所有时段。

## 改善办法一：先把下游无线与 LAN 做稳定

近距离、大吞吐设备可优先试私人 5GHz；跨墙或较远处再比较 2.4GHz 的实际丢包、延迟和稳定性。选择信道与带宽应看现场干扰和设备能力，而不是总选最大带宽。不要在没有证据时关闭 WMM、提高发射功率或修改国家码。

需要投屏、打印和设备发现时，先确认个人主 AP/LAN 的桥与隔离关系，再用两台下游设备实际收发。校园 WAN 仍应与私人 LAN 隔离；不要为方便发现设备放开校园侧防火墙。当前主 AP 同桥、未设四设备限额只是配置证据，**广播/组播互通和四台同时活跃尚未验收**。

本机的 DHCP 池与每频段 `maxsta` 有明确容量值，不能说无限设备。空口、路由器资源和校园侧策略也各自可能限制体验；MiniEAP 的恢复预算并不是下游设备数量限制。

## 改善办法二：在负载下测延迟，再考虑队列管理

空闲 ping 很低，不代表上传或下载占满时还会低。下一轮应在相同目标、相近时段，对空闲与适度负载下的延迟、丢包和吞吐分别取样，并观察 CPU。没有证明排队问题之前，不盲目关闭现有加速组件或加入限速规则。

若确实存在持续负载下的明显排队延迟，再评估队列管理。OpenWrt 的 [SQM 文档](https://openwrt.org/docs/guide-user/network/traffic-shaping/sqm)说明它针对 bufferbloat，但使用 CPU，并与硬件流卸载存在兼容取舍；它不是免费提高峰值速率的开关。是否适用于具体 RD03v2 构建，还要重新确认支持。不要把 OpenWrt 的配置键直接写进原厂系统。

对于当前已能工作的原厂环境，先保留可回滚的基线；每次只改变一个有证据支持的因素，再按相同负载验证。更换固件不应代替这一步。

## 改善办法三：把上游、测试目标和路由器瓶颈分开

先复核唯一认证进程、DHCP、DNS、接口源地址和正常 TLS 访问，再谈速度。然后尽量采用相近时间、同一目标与字节数，比较电脑直连、路由器有线下游和私人无线。只有一根线时往往只能分时测；应明确写出这项限制。

本次凌晨与上午的结果差异较大，但没有同时间、同条件对照，不能单凭它认定账号限速、校园拥塞或固件性能差。大对象 HTTP 403、部分响应或超时也可能使测试无效：每条连接都应分别核对状态码、收齐字节与完成情况，再计算完整阶段的吞吐。外层程序返回成功不代表每条传输成功。

认证稳定性也需要单独维护：保持成功客户端，正常交接做 Logoff，失败或未知尝试保留锁存。重启客户端来“测速”既改变条件，也可能引入会话问题。此前观察只取得约 6 小时 35 分钟的采样证据，进程已异常结束；不能把它当作 24 小时稳定性通过，更不能据此保证后续每次物理断线都会恢复。

这三项都可以先在已工作的原厂环境建立证据。只有在目标功能、硬件支持和恢复条件清楚后，才有依据评估另一系统是否值得单独研究。
